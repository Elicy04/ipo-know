## 数据库schema管理模式和工具
采用<span style="color:#000; background:#fff59d; font-weight:bold;">模式迁移</span>的方式
>**模式迁移**（也叫数据库模式版本迁移），是一种以增量、版本化的方式管理数据库模式（Schema）演进的工程化方法：通过编写带唯一版本标识的结构化变更脚本，自动化地对数据库表、字段、索引、约束、视图等结构对象执行新增、修改、下线操作，最终保障多环境下数据库结构一致性，且所有变更全程可追溯、可审计、可重复执行。

使用的技术栈: **Alembic + SQLAlchemy ORM**
核心原则：以 ORM 模型为结构定义单一真相源，迁移脚本为可执行变更载体，Git 为版本追溯底座，从机制上保证定义、执行、历史三者一致。

## 数据表设计规范
遵循「代码即定义、文档存逻辑、版本靠 Git」的原则，废弃全量快照式文件管理，收敛结构定义入口。

### 1. 结构定义唯一真相源：ORM 模型
所有数据表的字段、类型、约束、索引、注释、表级选项等完整结构定义，统一收敛至 `models/` 目录下的 SQLAlchemy ORM 模型代码中，作为数据库结构的唯一权威依据，不再单独维护手写全量表结构文档。

模型编写强制要求：
- 所有字段必须补充 `comment` 注释，明确业务含义、枚举取值规则等信息
- 索引、唯一约束、CHECK 约束等表级配置统一显式声明在 `__table_args__` 中
- SQLite 专属特性（如 `sqlite_autoincrement`、`WITHOUT ROWID`）需显式声明，避免隐式行为歧义
- 公共字段（如创建时间、更新时间、主键）通过抽象基类复用，保证全库规范统一

### 2. 设计文档：仅承载逻辑与规则
`docs/database/` 目录下仅维护设计逻辑类文档，不重复存储字段级结构定义，核心文档包括：
- `design.md`：存放全局设计规范（命名规则、软删除策略、索引设计原则）、SQLite 数据库级配置说明、核心架构决策与选型依据
- 重大结构变更的背景、目标与风险评估，统一沉淀在设计文档的变更日志章节中，随代码一同提交版本管理

### 3. 历史追溯依托 Git
表结构的历史迭代、变更细节、修改责任人全部通过 Git 提交历史与代码 diff 能力追溯，无需通过多份全量快照文件手动管理版本。

## 数据表schema修改完整流程
1. 明确变更目标与设计决策
   梳理本次表结构调整的业务需求与设计方案；重大变更需先在 `design.md` 的变更日志中记录变更背景、技术方案与风险点。

2. 更新 ORM 模型定义
   根据设计方案修改 `models/` 目录下的对应模型文件，保证字段、索引、约束等所有结构定义完整准确，与目标结构完全一致。

3. 编写 Alembic 迁移脚本
- **常规场景：自动生成迁移脚本**
  模型修改完成后，执行 `alembic revision --autogenerate -m <迁移描述>` 自动生成迁移脚本。
  > P.S.1 迁移描述会作为迁移脚本文件名的组成部分，禁止包含特殊字符或空格，具体命名规则详见 `docs/database/migration_description_spec.md`。
  > P.S.2 执行自动生成前，需确保当前数据库已执行完所有历史迁移脚本，否则会导致生成结果异常。
  > P.S.3 SQLite 环境下自动生成的脚本涉及字段修改、删除、重命名等操作时，默认通过批量重建表（`batch_alter_table`）实现，必须人工校验脚本逻辑，避免数据丢失风险。

- **特殊场景：手动编写迁移脚本**
  针对视图、触发器、大批量数据回填等无法自动生成的场景，手动编写迁移脚本。**必须同步更新 ORM 模型文件**，否则后续自动生成会产生反向回退脚本。

4. 执行迁移脚本，更新数据库结构
- 执行 `alembic upgrade head` 升级至最新版本。
- 仅开发/测试环境允许使用 `alembic downgrade <版本号>` 回退至指定版本；生产环境原则上禁止执行降级操作，风险变更优先通过新增正向迁移实现回滚。
